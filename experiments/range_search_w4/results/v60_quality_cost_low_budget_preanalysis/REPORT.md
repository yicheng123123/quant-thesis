# v60 — 有效修复轨迹的质量—成本整理与低预算预分析

## 结论

本轮只读现有文件并在 CPU 上重算。没有运行模型前向、GPU、量化、整数修复、新 held 或 PPL。v59 是四模型正式质量主表；v55/v56 是唯一进入主要低预算轨迹分析的完整传播有效修复。

逐组检查后确认：v55/v56 的已提交 group checkpoint 保存了每次接受事件的行、更新序号、C 二次型增量和该行累计候选评价数。因而能精确重放固定 C、固定输入下第 1/4/8/16/32 次接受后的**记录 search 二次型损失**及候选计数。重放与逐行 update/evaluation 计数吻合，最终二次型与独立 raw-X 初末端点吻合到日志精度；事件累加的最大浮点重建残差分别为 1.39e-17 和 2.78e-17。

中间状态没有逐次 raw-X 输出误差重算记录，因此本文不称这些为中间 raw-X 直接损失实测。它们是从冻结 Gram 路径保存的接受增量重建的 search 目标。

预算 8 在两种初始化下都只保留约 49% 的完整 32 次局部 search 下降；预算 16 保留约 72–73%。v56 的实测阶段支持一个条件估算：将预算降到 8，候选循环和周期 p 刷新约可省 160.5 秒，相当于完整 block timer 的约 3.02%；C 构建和全矩阵终态核验仍保留。收益—成本证据不足以支持新的低预算完整修复与质量评测。本轮建议结束质量扩展，不推荐新预算、不启动 GPU 实验。

v53 的历史表指出：v18 记录的 Transformers 4.49.0 支持 tuple decoder 返回，旧接口也声明 tuple；但没有历史逐调用返回类型记录，也没有穷尽重验全部历史前缀。因此 M1/M2 的校准协议受到记录支持、没有证据表明实际走了 Tensor 错误分支，但不能扩写成完整历史输入路径已独立证明。它们的 checkpoint 与原始 PPL 窗口来源经审计；v59 对固定 checkpoint 的统一重评回答其当前质量，不补证校准时的输入正确性。

v55/v56 的独立传播证据是各自修正接口后的新运行证据，不受 v45/v46/v49 的 UNKNOWN 扩大。v45/v46/v49 的实际 checkpoint 测量仍可保留为历史测量，但其校准传播未知，故不混入本轮的主轨迹分析或有效成本依据。

有效 M2 修复链的 block timer 可从已通过边界审计的分段相加：v51 block0 187.085 秒 + v54 layer1 238.934 秒 + v55 新修 layer2–23 4,240.102 秒 = 4,666.121 秒。它是三个运行目录中对应 block timer 的组合值，不是单一进程 wall，不含完整恢复/CPU/失败/诊断开销。v55 阶段表中的 C 构建 1,523.795 秒、初始化 14.567 秒、候选评分 92.797 秒、proposal/settle 35.860 秒、p refresh 70.149 秒、终态检查 1,780.198 秒对应其 layer2–23 新修 154 个 Linear；早期继承阶段单独留在 v51/v54 源记录。

条件成本情景只按 v56 已测 loop 计时计算：假定 scoring/propose 调用耗时随循环数线性变化，p refresh 仍按代码里的 1/8/16/24/32 触发。预算 8 情景下相关阶段从 232.636 秒估为 72.100 秒，节省 160.536 秒，即 5,317.371 秒 block timer 的 3.02%；预算 16 情景估计节省 107.024 秒（2.01%）。这些不是实测预测，且 C、输入传播、初始准备、终态检查和部署都按原样保留。细节与假设在 CONDITIONAL_COST_SCENARIO.csv。

v56 formal completion elapsed 为 5,699.771 秒，24 个 block timer 合计 5,317.371 秒；两者差额未单独归因。stage timers 中 host/launch、hash、commit 和同步开销无法全分解成纯计算与 CPU；恢复链的进程开销也不能由跨版本 block timer 精确还原。详见 STAGE_COSTS.csv 和 COST_SCOPE_NOTES.json。

## 解释限制、负结果与决定

- 没有逐更新 raw-X 直接损失；中间曲线严格限于已记录的固定-C search 二次型。独立 raw-X 检查覆盖各模块初始/最终端点，不覆盖每个中间状态。
- 低预算截取是在原始 32 次预算运行产生的各模块输入 X/C 上。预算减少会改变前序模块的模型张量与后续输入；这些历史局部截取不是从 layer0 开始的低预算完整模型。
- 现有日志没有任何低预算完整修复 wall、最终 checkpoint、传播验证、held 或 PPL。不能声称质量保持、完整校准加速或模型级质量迁移。
- 候选数下降约 74.6%（预算8），但条件 block timer 只省约 3.02%；候选次数比例不能当作耗时比例。32 次后半段仍贡献约 27% 的完整局部下降。
- 完整 v56 轨迹无候选拒绝、无 FP64 候选复核、无 candidate-evaluation cap 触顶；这不消除降低更新数后的部署/传播/质量风险。

**决定：不值得凭当前证据追加一次低预算完整修复，本轮作为毕设结果收束。** 原因是预算 8 只有约一半局部下降保留，预算 16 约四分之三；在全部完整终态检查和 Gram 成本照旧的条件下，理想循环缩放也只省约 2–3% 的完整 block timer。未观察到足以支撑质量—成本取舍的完整低预算模型证据，因此不推荐下一预算、不启动额外局部 GPU 试验。
